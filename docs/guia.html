Guia do Migrador
MySQL → PostgreSQL

Como funciona o script migrar.py e como testá-lo

O script migra uma base MySQL para PostgreSQL em três fases: valida o esquema e os dados antes de mexer no destino, copia tudo e, no fim, compara linha a linha e campo a campo para garantir que a conversão ficou certa. Resolve o que o pgloader deixava por fazer: FKs que viravam campos normais, registos órfãos, pesquisas de texto que passavam a distinguir maiúsculas, e triggers, procedures, views, eventos, índices FULLTEXT e colunas espaciais que ficavam para trás.

1. Porque não basta o pgloader

Na migração da base g_processes com o pgloader encontrámos estes problemas:

Problema com o pgloaderComo o script resolve
A versão do Ubuntu (3.6.10) falha com o MySQL 8 (76 fell through ECASE): não conhece a collation utf8mb3_tolower_ci. É Python puro (pymysql + psycopg); não depende da versão do pgloader.
Quando uma FK falha (registos órfãos), não a cria: a coluna fica um campo normal no PostgreSQL. Antes da FK, insere no pai os registos em falta. A FK é sempre criada e fica válida.
Perde AUTO_INCREMENT, valores por defeito, NOT NULL em datas e ON UPDATE CURRENT_TIMESTAMP. Recria tudo: identity com a sequência no maior id, defaults traduzidos, triggers para o ON UPDATE.
Texto passa a distinguir maiúsculas: WHERE email = 'Ana@x.com' deixa de encontrar ana@x.com. Aplica uma collation que ignora maiúsculas e acentos, como as _ci do MySQL.
Não migra triggers, procedures, funções, eventos, views, FULLTEXT nem colunas espaciais. Traduz o código para PL/pgSQL e cria-o no fim; FULLTEXT vira GIN; espaciais usam PostGIS.
Não diz se os dados chegaram todos iguais. Compara cada linha, cada campo e o tamanho de cada coluna, e grava um relatório.

2. Visão geral do fluxo

O script corre três fases, por esta ordem. Se a validação encontrar erros, pára antes de tocar no destino.

Fase 1 · Validarsó lê; não altera nada

  2. Ler o esquema MySQL
  3. Analisar os dados
  4. Planear tipos e nomes
  5. Mostrar incongruências
➜
Fase 2 · Migrarescreve no PostgreSQL
  1. Criar collations e tabelas
  2. Copiar os dados
  3. Chaves primárias e índices
  4. Acertar auto-incrementos
  5. Criar pais em falta
  6. Triggers ON UPDATE
  7. Criar e validar as FKs; criar triggers, procedures, views e eventos traduzidos
➜

Porque é que as FKs ficam para o fim? Se as FKs existissem durante a cópia, cada linha teria de esperar pela tabela-pai e qualquer órfão parava a migração. Criando-as no fim, a cópia nunca bloqueia, e o script consegue tratar os órfãos antes de as criar.

Com --modo pode correr só uma parte:

ModoO que fazQuando usar
validarSó a fase 1.Ver os problemas sem mexer no destino.
migrarFases 1 e 2.Migrar sem comparar (mais rápido).
verificarFases 1 e 3.Voltar a comparar uma migração já feita.
tudo (padrão)As três fases.Migração normal.

3. O fluxo passo a passo

Fase 1 — Validar

1

Ligar às bases

Lê os dados de conexão dos URLs --origem/--destino ou pergunta-os no terminal (a senha é pedida sem aparecer no ecrã). As duas ligações usam UTC, para as datas não mudarem de hora.

2

Ler o esquema do MySQL

Lê do information_schema: tabelas, colunas (tipo, NULL, valor por defeito, collation), índices, FKs, triggers, views, procedures e eventos.

3

Analisar os dados

Lê cada tabela uma vez e conta o que não passa direto para PostgreSQL: datas 0000-00-00, tinyint(1) com valores além de 0/1, carácter \0 em texto, ENUM com '', TIME negativo ou acima de 24h, bigint unsigned acima do limite.

4

Planear

Decide o tipo de cada coluna no PostgreSQL (secção 6), a collation de texto (secção 5), os valores por defeito e os nomes de índices e constraints (únicos no esquema, até 63 bytes).

5

Validar e mostrar incongruências

Verifica as FKs (tipos compatíveis, pai com chave única, órfãos), as permissões no PostgreSQL e se as tabelas já existem. Mostra tudo em três níveis: ERRO (impede a migração, salvo com --forcar), AVISO (migra, mas reveja) e INFO.

Fase 2 — Migrar

6

Criar collations e tabelas

Cria o esquema, as collations mysql_ci_ai/mysql_ci, a tabela migracao.registos_criados e as tabelas com colunas, NOT NULL, defaults, CHECK dos ENUM e comentários. Ainda sem chaves nem FKs. Com --substituir apaga antes as que já existem.

7

Copiar os dados

Tabela a tabela, em lotes de 5000 linhas (--lote), com o comando COPY do PostgreSQL (o mais rápido). Pelo caminho converte valores: datas zero para NULL, remove \0, 0/1 para booleano. Cada tabela é uma transação: se falhar, não fica a meio.

8

Chaves primárias, índices e UNIQUE

Criados depois dos dados porque é muito mais rápido do que actualizá-los linha a linha. Se uma FK aponta para colunas sem índice único (o MySQL permite, o PostgreSQL não), cria esse UNIQUE.

9

Acertar auto-incrementos

Cada coluna identity passa a continuar a partir do maior id existente, para o próximo INSERT não colidir.

10

Criar os pais em falta

Para cada FK com órfãos, insere no pai os registos com as chaves em falta (secção 4).

11

Triggers de ON UPDATE

O PostgreSQL não tem ON UPDATE CURRENT_TIMESTAMP; o script cria um trigger que actualiza a coluna (ex.: updated_at) sempre que a linha muda.

12

Criar as FKs e os objetos de código

Cria cada FK e valida-a contra os dados existentes; com os pais criados no passo 10, ficam todas válidas. Depois cria as funções, procedures, views, triggers e eventos traduzidos (secção 6). Ficam para o fim de propósito: se os triggers existissem durante a cópia, disparavam em cada linha copiada.

Fase 3 — Verificar

13

Comparar as duas bases

Para cada tabela: confirma as colunas (tipo, NULL, default, collation); lê as duas bases ordenadas pela chave primária e compara cada linha e cada campo; soma o tamanho e os valores preenchidos de cada coluna. Depois confirma que todas as FKs, índices e sequências existem. Os registos criados no passo 10 são reconhecidos e não contam como diferença.

14

Relatório e resultado

Grava em relatorios/ um .md (legível), um .json (tudo, com exemplos das diferenças) e um .sql (comandos executados). Termina com um código de saída (secção 7).

4. Registos órfãos: pais criados antes da FK

Um órfão é uma linha que aponta para um registo que não existe. Exemplo: a tabela anexos tem processo_id = 999, mas não há processo 999. No MySQL isto acontece quando os dados entraram antes de a FK existir ou com FOREIGN_KEY_CHECKS=0.

pgloader

A FK falha → não é criada → processo_id fica um campo normal. A base deixa de impedir novos órfãos.

migrar.py (padrão)

Insere em processo um registo com id 999 → cria a FK → a FK fica válida e protege os dados daí para a frente.

Que valores levam os registos criados

Só a chave vem do filho. Os outros campos obrigatórios (NOT NULL sem valor por defeito) recebem:

Tipo de campoValor
TextoREGISTO EM FALTA (criado na migração) (cortado ao tamanho da coluna)
Texto ou número com UNIQUEUm valor que não se repete (maior valor + 1, ou texto aleatório)
Número0
Data / data e hora1970-01-01
ENUMO primeiro valor da lista
Booleanofalse
Campo que é FK para outra tabelaUm registo que já exista nessa tabela

Onde ficam anotados

Cada registo criado é gravado em migracao.registos_criados, num esquema separado:

SELECT tabela, chave, motivo FROM migracao.registos_criados;

 tabela |  chave   |               motivo
--------+----------+------------------------------------
 pais   | ["XX"]   | FK fk_cid_pais: cidade(pais)
 zona   | ["MZ",9] | FK fk_ponto_zona: ponto(pais, num)

Depois da migração pode completar esses registos com os dados certos, ou apagar os filhos que não interessam e a seguir os registos criados.

Alternativa: com --orfaos not-valid os dados ficam exactamente como no MySQL e a FK é criada NOT VALID: existe no esquema e protege os dados novos, mas as linhas antigas não são verificadas. Depois de corrigir os órfãos, valide-a com ALTER TABLE anexos VALIDATE CONSTRAINT nome_da_fk;

Melhor ainda: corrigir os órfãos no MySQL antes de migrar, como foi feito com os anexos 114–116 e o error_log 8. A validação (fase 1) lista cada órfão com exemplos.

5. Maiúsculas e acentos: WHERE igual ao MySQL

As colunas de texto da base usam utf8mb4_general_ci e utf8mb4_0900_ai_ci. O ci quer dizer case insensitive: o MySQL ignora maiúsculas e acentos nas comparações. O PostgreSQL, por defeito, compara de forma exacta. Sem tratamento, logins e pesquisas da API deixariam de encontrar registos.

ConsultaMySQLPostgreSQL normalPostgreSQL com o script
WHERE email = 'JOSE@GMAIL.COM'
(gravado jose@gmail.com)		encontranão encontraencontra
WHERE nome = 'MOCAMBIQUE'
(gravado Moçambique)		encontranão encontraencontra
WHERE nome LIKE 'orf%'
(gravado Órfã)		encontranão encontraencontra
UNIQUE com 'MZ' e 'mz'recusaaceita os doisrecusa

Como funciona

O script cria no esquema de destino duas collations ICU não determinísticas e aplica-as a cada coluna de texto conforme a collation que ela tinha no MySQL:

Collation no MySQLNo PostgreSQLRegra
*_ci, *_ai_ci (general, unicode, 0900)mysql_ci_aiignora maiúsculas e acentos
*_as_cimysql_ciignora só maiúsculas
*_bin, *_cs(nenhuma)comparação exacta

Com isto, =, IN, LIKE, GROUP BY, DISTINCT, UNIQUE e FKs comportam-se como no MySQL, sem mudar o código da API. No psql a coluna aparece assim:

 Column |         Type          |  Collation
--------+-----------------------+-------------
 email  | character varying(255)| mysql_ci_ai

Limitações

  • PostgreSQL 18 ou superior para LIKE. Em versões anteriores, LIKE dá erro nestas colunas (o script avisa na validação). O servidor actual é o 18.6.
  • ILIKE e expressões regulares (~) dão erro nestas colunas. Use LIKE, que já ignora maiúsculas. A API usa .like() 51 vezes e nunca ilike nem regex em SQL, por isso não precisa de alterações.
  • Para a comparação normal do PostgreSQL use --comparacao-texto exata; nesse caso a aplicação tem de usar lower() ou ILIKE.

tinyint(1) cujo nome termina em _id ou que faz parte de uma FK fica smallint: é um número, não um sim/não. Na base real isto acontece com grupo.inferior_id, que a API trata como Integer.

Triggers, procedures, funções, eventos e views

O script traduz o código do MySQL para PL/pgSQL (ficheiro objetos.py). O SQL normal (expressões, SELECT, INSERT...) é traduzido com a biblioteca sqlglot; a parte procedimental é traduzida pelo próprio script:

MySQLPostgreSQL
CREATE TRIGGER t BEFORE INSERT ... BEGIN ... ENDfunção t_fn() em PL/pgSQL + CREATE TRIGGER t ... EXECUTE FUNCTION t_fn()
PROCEDURE / FUNCTIONPROCEDURE / FUNCTION ... LANGUAGE plpgsql
EVENT ... EVERY 1 DAY STARTS '... 03:30'procedure evento_<nome>(), agendada no pg_cron (30 3 * * *) ou, sem pg_cron, com a linha de crontab pronta no relatório
VIEWCREATE VIEW com o SQL traduzido (criadas pela ordem das dependências)
DECLARE, SET, IF/ELSEIF, CASE, WHILE, REPEAT, LOOP, LEAVEequivalentes em PL/pgSQL
SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = mRAISE EXCEPTION USING ERRCODE = '45000', MESSAGE = m
IFNULL, <=>, CONCAT, IF(), DATE_ADD…COALESCE, IS NOT DISTINCT FROM, ||, CASE, + INTERVAL…
estado = 1 numa coluna que passou a booleanestado = TRUE

A verificação (fase 3) confirma que cada objeto existe e que cada view devolve exactamente as mesmas linhas que no MySQL. Nos testes, os triggers, a procedure e a função traduzidos deram os mesmos resultados e as mesmas mensagens de erro nas duas bases.

O que ainda precisa de revisão manual: cursores e handlers (DECLARE ... CURSOR/HANDLER), variáveis de sessão (@var) e SQL dinâmico (PREPARE/EXECUTE). Esses objetos não são criados: vão para relatorios/migracao_<data>_por_rever.sql, com o código original, o motivo e a tentativa de tradução, prontos a corrigir e executar com psql -f. Na base real não há nenhum.

Índices FULLTEXT e colunas espaciais

  • FULLTEXT → índice GIN sobre to_tsvector('simple', coalesce(coluna, '')). As pesquisas MATCH(col) AGAINST('texto') da aplicação passam a to_tsvector('simple', coalesce(col, '')) @@ plainto_tsquery('simple', 'texto').
  • Espaciais (point, polygon, geometry…) → PostGIS geometry(Point,4326) etc., com o SRID e a ordem longitude/latitude certos; índices SPATIAL → GiST. Precisa do PostGIS no servidor (sudo apt install postgresql-18-postgis-3); sem ele a validação dá ERRO e explica o que instalar.

7. Executar passo a passo

Do zero até aos resultados verificados. Os comandos são para Linux (Ubuntu); o terminal deve estar na pasta do script.

1

Instalar o Python (uma vez por máquina)

É preciso Python 3.10 ou mais recente, com o módulo venv:

python3 --version                                   # deve mostrar 3.10 ou superior
sudo apt update && sudo apt install -y python3 python3-venv python3-pip

Para os testes de verificação também ajudam os clientes mysql e psql (sudo apt install -y mysql-client postgresql-client) e o Docker (só para os testes 1–6).

2

Ter a pasta do script

A pasta migrador/ tem tudo o que é preciso:

migrador/
├── migrar.py           # o script principal
├── objetos.py          # tradução de triggers, procedures, views, eventos
├── requirements.txt    # dependências Python
├── testes/             # casos.sql e casos_espaciais.sql
└── docs/guia.html      # fonte deste guia
cd ~/Programming/"Projects - Real"/Acsun/Testing/migrador
3

Criar o ambiente Python e instalar as dependências (uma vez)

O ambiente virtual (.venv) guarda as bibliotecas dentro da pasta, sem mexer no Python do sistema:

python3 -m venv .venv
.venv/bin/pip install -r requirements.txt           # pymysql, psycopg, sqlglot
.venv/bin/python -c "import pymysql, psycopg, sqlglot; print('ok')"   # deve mostrar ok
4

Preparar as duas bases

MySQL (origem): um utilizador que só leia chega. Como administrador do MySQL:

CREATE USER 'migra'@'%' IDENTIFIED BY '...';
GRANT SELECT, SHOW VIEW, TRIGGER, EVENT ON g_processes.* TO 'migra'@'%';
GRANT SHOW_ROUTINE ON *.* TO 'migra'@'%';    -- MySQL 8.0.20+: ler o código de procedures e funções

PostgreSQL (destino): uma base vazia, de um utilizador que possa criar tabelas:

createdb -h 127.0.0.1 -U samuel g_processes

Confirme que consegue ligar às duas:

mysql -h 127.0.0.1 -u migra -p g_processes -e "SELECT COUNT(*) FROM information_schema.tables"
psql  -h 127.0.0.1 -U samuel -d g_processes -c "SELECT version()"
5

Validar (sem mexer no destino)

.venv/bin/python migrar.py --modo validar \
  --origem  mysql://migra@127.0.0.1:3306/g_processes \
  --destino postgresql://samuel@127.0.0.1:5432/g_processes

As senhas são pedidas no terminal. Leia a lista: ERRO tem de ser corrigido antes de migrar, AVISO deve ser revisto, INFO é só informação. Na base real dá 0 erros.

6

Migrar e verificar

.venv/bin/python migrar.py \
  --origem  mysql://migra@127.0.0.1:3306/g_processes \
  --destino postgresql://samuel@127.0.0.1:5432/g_processes

O script repete a validação, pergunta Migrar 91 tabelas ...? [s/N] (responda s), migra e verifica. Se a base de destino já tiver as tabelas, junte --substituir.

7

Verificar os resultados

  1. A última linha do terminal deve dizer Concluído: os dados no PostgreSQL são iguais aos do MySQL, e o código de saída deve ser 0: 
    echo $?
  2. O relatório relatorios/migracao_<data>.md: resumo, avisos e a tabela por tabela (linhas MySQL, linhas PostgreSQL, iguais, diferentes, em falta). O .json tem exemplos de cada diferença; o .sql tem todos os comandos executados.
  3. Objetos por rever: se existir relatorios/migracao_<data>_por_rever.sql, corrija-o e execute com psql -h 127.0.0.1 -U samuel -d g_processes -f ficheiro.sql.
  4. Confirmar no PostgreSQL: 
    psql -h 127.0.0.1 -U samuel -d g_processes

  5. No navegador: Adminer em http://localhost:8080 (sistema PostgreSQL).
  6. Mais tarde: para voltar a comparar as duas bases, sem migrar de novo, use --modo verificar.

8. Como testar

Faça os testes por esta ordem. Os testes 1 a 6 usam bases de teste com os casos difíceis; os testes 7 e 8 usam uma cópia da base real. Nunca teste directamente contra a base de produção do PostgreSQL.

Teste 1 — Preparar a base de casos difíceis

Objectivo: ter um MySQL temporário com dados problemáticos de propósito.

O ficheiro testes/casos.sql cria a base casos com: datas zero, órfãos (simples, composto e para coluna sem índice único), chave de texto 'PT'/'pt', unsigned, JSON, BLOB, BIT, TIME acima de 24h, ENUM com '', carácter \0, tabela sem chave primária, view e índice FULLTEXT, e ainda 3 triggers (um deles com cursor, de propósito), uma procedure com ciclo, uma função, um evento e uma view com JOIN.

# MySQL temporário na porta 3307 (não mexe no MySQL principal)
docker run -d --rm --name mysql-teste -e MYSQL_ROOT_PASSWORD=teste -p 3307:3306 mysql:8.0
# esperar ~20 s até arrancar, depois carregar os casos
docker exec -i mysql-teste mysql --default-character-set=utf8mb4 -uroot -pteste < testes/casos.sql
# base de destino vazia
createdb -h 127.0.0.1 -U samuel casos_teste

Teste 2 — Migração completa dos casos difíceis

Objectivo: confirmar que todos os problemas são detectados, tratados e verificados.

.venv/bin/python migrar.py --origem mysql://root:teste@127.0.0.1:3307/casos \
  --destino postgresql://samuel@127.0.0.1:5432/casos_teste --sim
echo $?        # deve mostrar 0

Resultado esperado:

  • Fase 1 lista avisos de datas zero, tinyint(1), TIME, ENUM, \0, FULLTEXT, tabela sem PK, view e 3 órfãos (XX, ('MZ', 9) e nenhuma). 'PT' não aparece como órfão, porque 'PT' = 'pt', como no MySQL.
  • Fase 2 mostra 3 registo(s)-pai em falta criados, 3 FKs criadas (3 validadas, 0 NOT VALID) e 7/8 triggers, procedures, funções, eventos e views criados (1 por rever à mão) — o trigger com cursor.
  • Fase 3 mostra pais 3 → 4 ok (+1 criada(s) para FKs) e zona 3 → 5 ok (+2 ...).
  • Fase 3 mostra Triggers, procedures, funções, eventos e views: 7/8 presentes (views com os mesmos dados).
  • Termina com Concluído: os dados no PostgreSQL são iguais aos do MySQL e existe o ficheiro relatorios/migracao_<data>_por_rever.sql com o trigger trg_com_cursor.

Teste 3 — A verificação apanha diferenças?

Objectivo: provar que a fase 3 não diz "ok" sem comparar de verdade.

# estragar dados no PostgreSQL de propósito
psql -h 127.0.0.1 -U samuel -d casos_teste -c "UPDATE zona SET descricao='SUL' WHERE num=2"
psql -h 127.0.0.1 -U samuel -d casos_teste -c "INSERT INTO pais(codigo,nome) VALUES ('ZZ','extra')"

.venv/bin/python migrar.py --modo verificar --origem mysql://root:teste@127.0.0.1:3307/casos \
  --destino postgresql://samuel@127.0.0.1:5432/casos_teste
echo $?        # deve mostrar 1
  • zona: 1 diferente(s) ... campos: descricao (a verificação compara o valor exacto: 'SUL' ≠ 'sul').

10. Problemas comuns

Mensagem / sintomaCausa e solução
Não consegui ligar ao MySQL/PostgreSQL (saída 3) Host, porta, utilizador ou senha errados, ou o serviço parado. Teste com mysql/psql.
Tabelas já existem no destino (ERRO) A base de destino não está vazia. Use outra base ou --substituir (apaga e recria essas tabelas).
Sem permissão no destino O utilizador do PostgreSQL não pode criar objectos: GRANT CREATE ON DATABASE ... TO ... ou use o dono da base.
FK para colunas sem unicidade (ERRO) A FK aponta para colunas com valores repetidos; o PostgreSQL não permite. Corrija os duplicados no MySQL.
nondeterministic collations are not supported for ILIKE A aplicação usa ILIKE numa coluna com mysql_ci_ai. Troque por LIKE (já ignora maiúsculas).
LIKE não funciona antes do PostgreSQL 18 (AVISO) Actualize o PostgreSQL para o 18 ou use --comparacao-texto exata.
Pai em falta não criado (AVISO) Não foi possível inserir o registo-pai (ex.: CHECK ou campo sem valor possível). A FK fica NOT VALID; corrija à mão.
Por rever à mão (Trigger/Procedure...) (AVISO) O código usa cursores, handlers, @variáveis ou SQL dinâmico. Corrija a tradução em *_por_rever.sql e execute-a com psql -f.
Colunas espaciais sem PostGIS (ERRO) Instale o PostGIS no servidor: sudo apt install postgresql-18-postgis-3.
View devolve dados diferentes (ERRO) A tradução da view não dá o mesmo resultado (ex.: função com comportamento diferente). Veja a view no .sql do relatório e ajuste-a.
Verificação lenta em tabelas muito grandes Nos ensaios use --sem-comparar-linhas; deixe a comparação completa para a migração final.
Acentos estragados (MoÃ§ambique) Dados carregados no MySQL com o charset errado. Carregue sempre com --default-character-set=utf8mb4.
